# ADR-003: Estructura del Repositorio y Estrategia de Ramas Git

* **Estado:** Propuesto
* **Fecha:** Octubre 2026
* **Autores:** Equipo de Desarrollo HegiaStock (4 integrantes)

## Contexto
El equipo de 4 integrantes requiere una convención clara de trabajo colaborativo en GitHub para evitar conflictos de código, asegurar la trazabilidad con los requerimientos (`requirements.md`)[cite: 1] y mantener la frontera arquitectónica (no incluir código de IA/MCP hasta la Unidad 3)[cite: 1] en un plazo de 10 semanas[cite: 1].

## Alternativas Consideradas

### 1. GitHub Flow (Flujo basado en ramas de características `feature/`)
* **Ventajas:** Simple, directo y adecuado para equipos pequeños. La rama `main` siempre permanece estable y desplegable.
* **Desventajas:** Requiere disciplina en la revisión de Pull Requests (PR) para no romper la rama principal.

### 2. GitFlow (Ramas `main`, `develop`, `feature/`, `release/`, `hotfix/`)
* **Ventajas:** Control riguroso de fases y versiones.
* **Desventajas:** Excesiva burocracia de ramas para un proyecto de 10 semanas con 4 desarrolladores[cite: 1].

## Decisión
Adoptar **GitHub Flow** ordenando el repositorio en carpetas por módulos de dominio (`src/modules/`), protegiendo la rama `main` y obligando al uso de ramas por historia de usuario (`feature/HU01-consulta-stock`)[cite: 1].

## Consecuencias
* **Positivas:** Integración continua fluida, historial limpio y aislamiento claro del trabajo de cada integrante.
* **Negativas:** Requiere coordinación del equipo para resolver conflictos al fusionar Pull Requests.
* **Deuda aceptada:** Sin entorno de *Staging* separado; las pruebas se realizan localmente antes del *Merge* a `main`.

## Criterio de Reversión
Si ocurren más de dos sobrescrituras accidentales de código en `main`, se bloquearán los *pushes* directos activando la regla de aprobación obligatoria de PRs en GitHub.
