# ADR-002: Selección del Motor de Base de Datos y Estrategia de Persistencia

* **Estado:** Propuesto
* **Fecha:** Octubre 2026
* **Autores:** Equipo de Desarrollo HegiaStock (4 integrantes)

## Contexto
El sistema HegiaStock requiere almacenar el catálogo de productos de inventario (solo lectura)[cite: 1], la estructura espacial del almacén (pasillos/estantes)[cite: 1] y registrar las solicitudes de verificación física con correlativo único «VER-NNN» (HU05)[cite: 1]. Esta decisión está regida por las restricciones de aplicación web ligera local, plazo de 10 semanas[cite: 1], cero almacenamiento de datos personales (Ley N.º 29733)[cite: 1] y preparación del punto de integración de solo lectura para el Servidor MCP en la Unidad 3[cite: 1].

## Alternativas Consideradas

### 1. SQLite 3 (Base de datos embebida en archivo local `hegiastock.db`)
* **Ventajas:** Cero instalación/configuración de servidor externo, soporte nativo en Python 3.11, velocidad de lectura extremadamente alta (cumple $\le 3\text{ s}$)[cite: 1] y fácil respaldo en el repositorio.
* **Desventajas:** Concurrencia limitada de escritura (no crítico, ya que la mayoría de operaciones son lecturas — proporción exacta: **PENDIENTE, confirmar con métricas del equipo**)[cite: 1].
* **Requisito de instalación:** Módulo `sqlite3` de la biblioteca estándar de Python [VERIFICAR][cite: 1].

### 2. MySQL / MariaDB (Servidor relacional dedicado)
* **Ventajas:** Alta capacidad para múltiples escrituras concurrentes y herramientas de administración gráfica.
* **Desventajas:** Requiere instalar y mantener un servicio de base de datos independiente, añadiendo complejidad de configuración al equipo.
* **Requisito de instalación:** Servicio MySQL corriendo en servidor local o contenedor [VERIFICAR].

## Decisión
Adoptar **SQLite 3** como motor de persistencia local relacional, operando el catálogo en modo estricto de solo lectura y restringiendo la escritura a la tabla de tickets de verificación (`tickets_verificacion`)[cite: 1].

## Consecuencias
* **Positivas:** Despliegue inmediato sin dependencias de infraestructura y máxima velocidad de respuesta en lecturas[cite: 1].
* **Negativas:** La base de datos vive en un archivo local que debe protegerse de modificaciones no autorizadas[cite: 1].
* **Deuda aceptada:** Bloqueo de archivo completo durante operaciones de escritura (aceptable por el bajo volumen de creación de tickets)[cite: 1].
* **Deuda aceptada — Divergencia de motor (Hallazgo C13):** El script DDL en `database/schema.sql` usa sintaxis MySQL/MariaDB (XAMPP) para el entorno de desarrollo y aprendizaje del equipo. El motor de producción de la Unidad 2 es SQLite 3. La migración del DDL a SQLite no requiere cambios en la capa de servicio (SQLAlchemy abstrae el motor); solo cambia la cadena de conexión en `backend/core/database.py`. **PENDIENTE del equipo:** confirmar que el DDL MySQL se ejecuta correctamente en XAMPP y documentar el script de carga equivalente para SQLite.

## Criterio de Reversión
Si antes de la **Semana 7** el volumen de pruebas concurrentes de los 12 usuarios ocasiona bloqueos de base de datos (`database is locked`), se migrará a **PostgreSQL o MySQL**[cite: 1].
